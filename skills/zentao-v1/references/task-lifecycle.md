# 任务生命周期与防错规则

适用于用户要求创建任务、开始任务、完成任务、关闭任务，或要求“创建后直接完成并关闭”的场景。

## 状态机

```text
创建任务
   ↓ 回读 wait
开始任务（仅 wait 执行）
   ↓ 回读 doing，并记录 realStarted
完成任务
   ↓ 回读 done
关闭任务
   ↓ 回读 closed
```

四个阶段是四次独立的业务写入。不能把它们合并为一次 `updateTask`，也不能因为上一步返回成功就跳过下一步的回读。

## 总体执行协议

每个阶段都执行：

```text
READ → VALIDATE → PREPARE → CONFIRM → WRITE_ONCE → READ_BACK
```

具体规则：

1. `READ`：读取任务详情，确认任务 ID、执行 ID、负责人、当前状态和工时字段。
2. `VALIDATE`：只使用用户明确提供的数据和实时回读的数据；不猜测实际开始时间、实际完成时间或消耗工时。
3. `PREPARE`：在写入前确定当前阶段的最终字段；“完成并关闭”也要展示为开始、完成、关闭三个阶段。
4. `CONFIRM`：没有用户明确授权时不得写入。用户已经明确说“帮我完成并关闭”时，授权范围仅覆盖目标任务的这三个状态变更。
5. `WRITE_ONCE`：同一阶段同一份字段只提交一次。超时、连接中断或响应不明时先回读，禁止盲目重试。
6. `READ_BACK`：以任务详情中的状态和关键字段为成功依据，不以 HTTP 状态码或接口文本为依据。

若写入因明确的参数校验失败而失败，且回读确认状态没有变化，可以基于错误原因重新准备一份修正后的字段；不得重复提交原请求。权限失败、认证失败、网络不明或写入结果不明时停止并报告。

## 阶段一：创建任务

### 前置核对

- 确认 `executionId`、任务名称和任务类型。
- 页面“事务”映射为接口类型 `affair`。
- 日常任务默认负责人为当前 MCP 连接账号；无法确认时先询问用户。
- 任务名称保留一个 `【类型】` 前缀；已有前缀时不重复添加。
- 用户提供的编号内容合并为一条任务名称，不自动拆分。

### 写入和回读

- 使用 `createTask`，不要用任务更新接口代替创建。
- 创建请求只提交用户明确提供的字段和技能中的日常默认值。
- 创建成功后立即使用 `getTaskDetail` 回读，并核对任务 ID、名称、执行 ID、类型、负责人和预计工时。
- 正常的新任务状态应为 `wait`；只有回读确认后才进入开始阶段。
- 如果创建接口已返回任务 ID 但回读失败，不得重复创建；先报告“已写入但未核验”。

## 阶段二：开始任务

- 先读取当前状态。
- 当前为 `wait` 时，使用 `startTask`，`left` 使用任务详情中的预计工时，`consumed` 默认为 `0`，备注默认为空。
- 开始后必须回读为 `doing`，并保存回读中的 `realStarted`。
- 当前已经是 `doing` 时，不重复调用 `startTask`；直接读取并保存已有的 `realStarted`。
- 当前已经是 `done` 或 `closed` 时，跳过开始阶段，不得把已完成任务重新开始。
- `realStarted` 必须来自禅道任务详情或开始接口的回读，不能用预计开始日期代替，也不能凭空生成。

## 阶段三：完成任务

### 前置状态和工时

- 只有当前状态为 `doing` 才能完成。
- 当前为 `wait` 时，必须先完成阶段二并回读为 `doing`；不得直接调用完成接口。
- 当前为 `done` 时，跳过完成写入，先核对是否可以关闭。
- 当前为 `closed` 时，任务流程已经结束，不得重复写入。
- `consumed` 表示本次完成操作新增的实际消耗工时，不是任务累计消耗工时。
- 用户明确说“用时 8 小时”时，完成请求使用本次消耗 `8`；如果用户没有提供实际消耗，不能擅自用预计工时替代。
- 正常完成的剩余工时语义为 `left=0`；不得在完成后继续保留未说明的剩余工时。

### 实际开始时间与实际完成时间

这是禅道 21.7.x 完成接口的强制规则：

1. `realStarted` 必须提交，并且必须使用当前任务详情中已经记录的实际开始时间。
2. `finishedDate` 必须提交实际完成的日期和时间，建议格式为 `YYYY-MM-DD HH:mm`。
3. 不能只提交 `YYYY-MM-DD`。禅道会将纯日期按当天零点处理；如果任务当天较晚才开始，会被判定为“实际完成早于实际开始”并返回 400。
4. 必须满足 `finishedDate >= realStarted`。如果实际开始时间和完成时间在同一天，完成时间至少应晚于或等于开始时间。
5. 本用户的日常任务时间约定为当天 `08:00–20:30`。用户未另外指定时，日常任务完成时间使用当天 `20:30`；日期仍以任务详情和当前日期为准，不得使用未来日期。
6. 如果服务端返回时间带时区，例如 `2026-09-05T09:21:20Z`，仍以回读值作为 `realStarted`，完成时间应传一个明确晚于它的本地日期时间。

### 写入和回读

- 使用 `finishTask`，把本次消耗、`realStarted`、`finishedDate`、`left=0` 和备注作为最终字段一次提交。
- 完成后使用 `getTaskDetail` 回读，必须确认状态为 `done`。
- 回读仍为 `doing`、返回 400 或状态不明时，不得进入关闭阶段；先停止并回读核对。

## 阶段四：关闭任务

- 先读取任务详情，只有状态为 `done` 才能关闭。
- 使用 `closeTask` 单独提交关闭操作，备注默认为空。
- 关闭后再次使用 `getTaskDetail` 回读，必须确认状态为 `closed`。
- `done` 不等于 `closed`；完成回读为 `done` 后仍必须单独调用关闭接口。
- 如果任务不是 `done`，不得强行关闭，也不得用 `updateTask` 直接改成 `closed`。

## “创建并完成并关闭”的安全执行模板

用户明确授权整条流程时，按下面顺序执行，不能一次性并发调用：

1. `createTask` → 回读 `wait`。
2. `startTask` → 回读 `doing`，记录 `realStarted`。
3. `finishTask` → 传 `consumed`、`left=0`、`realStarted`、明确的 `finishedDate` → 回读 `done`。
4. `closeTask` → 回读 `closed`。

任何一步失败、响应不明或回读状态不符合预期，立即停止后续写入；先回读当前状态，不重复提交，也不切换到其他禅道 MCP 或浏览器模拟补救。
