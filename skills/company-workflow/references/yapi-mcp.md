# YApi MCP 工作流

仅在用户请求涉及 API 契约、YApi 文档或契约对应的前端请求定义时读取本参考。只使用当前环境实际提供的 `yapi_auto_mcp` 工具，不臆造工具名或通过其他通道绕过 MCP。

## 工具路由

- `yapi_list_projects`：识别项目及项目 ID。
- `yapi_get_categories`：读取项目分类和分类下接口，用于核对完整候选范围。
- `yapi_search_apis`：按名称、路径、项目或标签检索候选接口。
- `yapi_get_api_desc`：读取指定项目中的 API 详情及请求、响应定义。
- `yapi_save_api`：按已确定的项目和分类创建或更新接口。

按当前工具清单调用同名 MCP 工具。YApi 搜索结果可能最多只显示 20 条，且筛选结果不能单独证明接口不存在；先确认项目，再结合分类清单按**精确 path + method** 核验。相同 path 的不同 method 是不同接口。YApi Mock 地址也按 method 严格匹配，验证时请求方法必须与定义一致。

## 查找和设计契约

1. 从当前 YApi 连接确认项目、项目 ID、基础路径和分类 ID。不要把某个项目（例如 PIM 的 `274`）硬编码成通用默认值。
2. 通过分类清单或搜索定位候选项，再读取精确接口详情。核对路径、方法、标题、分类、请求体类型、请求 schema、响应 schema、状态和描述。
3. 先找用户指定的 PRD、已批准的接口设计或现有契约。沿用相邻列表/详情接口时，只复用已证实的共通字段；明确标出为推导的部分。若缺少会改变业务语义的字段或返回规则，先提问，不把前端实现当后端承诺。
4. 仅在契约明确枚举值时使用 `enum`，并保留字段正确的数据类型。示例、候选项、Mock 值不是枚举依据。
5. 分清 YApi 项目基础路径与业务接口 path。**web-base PIM** 的商品平台项目基础路径为 `/goods/goods`，YApi 单接口 path 通常不含该前缀，而页面的 `useRequest` path 会带 `/goods/goods/`；其他项目必须重新读取确认。
6. **web-base PIM** 页面请求沿用可搜索、可类型检查的 path 模式（例如 `useRequest('/goods/goods/xxx')`），不要改成 `goods_post_xxx` 语义 key 模式。此规则只适用于已采用该约定的项目，其他项目按其现有请求规范执行。

## 创建和更新

- 创建前先按精确 path + method 查重，并核对目标分类；有同路径同方法接口时，先判断是更新还是另一个业务契约，不重复创建。
- 更新前必须 `yapi_get_api_desc` 读取完整现状。`yapi_save_api` 是全对象写入：回写时保留未修改的标题、路径、方法、分类、请求参数/请求体、请求头、响应、状态、标签和文档，只替换用户要求或契约确定的字段。避免无关格式化、字段重排和描述改写。
- 新建时先确定字段结构和分类，再调用 `yapi_save_api`；不确定的响应字段、required 规则或 ID 命名不能从相邻接口擅自复制成已确认契约。
- 保存后用 `yapi_get_api_desc` 回读目标接口。核对 API ID、标题、path、method、请求/响应类型与 schema、分类和状态；只依据回读结果报告保存成功。

## 与前端 API 类型衔接

- 修改 YApi 契约后，检查业务调用 path 是否登记在该项目的 `MonoApiMap`/请求映射中，以及映射的请求和响应类型是否包含此次契约字段。
- 优先更新项目的权威契约输入，再使用项目既有生成链路更新 API map 和类型。不要手改生成的 `typing.ts` 来伪造契约；当快照或生成器落后时，先查清生成输入和输出范围，避免整目录重生成覆盖无关代码。不要用 `as any` 只为压掉缺失路由类型。
- 对从列表分页接口派生的预览接口，若契约明确是“同一分页请求 + 目标记录主键 ID”，只增加对应主键参数；不要把导出字段、导出配置或无关操作参数带入预览请求。
- 路由类型修复后区分静态类型映射、页面请求行为和后端服务是否实现。YApi 有定义并不等于后端已部署。
- **web-base PIM** 的 YApi 类型生成链路以仓库脚本为准：YApi 详情快照 → 转换为 OpenAPI → 生成 `apps/pim/request/record/`。重新生成前检查脚本实际输入、输出和工作区改动，避免整目录覆盖无关变更；不要输出或复制 YApi token 等凭据。
- 排查生成结果缺失或类型退化为 `object` 时，确认转换器是否处理了无顶层 `$ref` 的 inline object schema。PIM 的历史生成器曾因未收集此类 schema，导致生成的 `typing.ts` 为空或 DTO 丢失；应修正/使用权威转换链路，再检查生成产物，不要直接手改生成类型文件。

## Mock 和验证边界

- `yapi_save_api` 成功只证明定义保存，不证明 YApi Mock 引擎能执行，也不证明真实后端行为。
- 当契约需要 YApi 字段表格文档时，保持响应的 JSON Schema 模式；修改 Mock 时在字段 schema 添加 `mock` 规则。嵌套 object 要按 Mock 需要补 `required`，数组数量用 `minItems`/`maxItems`，不要给 array 字段本身加 `mock`。
- YApi Mock 只生成 `required` 中的字段；若需要返回嵌套对象和其子字段，应逐层核对对应 `required`。动态 mock 表达式若导致 Mock 引擎报错，先与同类正常接口对照 schema，检查 required、嵌套数组和复杂表达式，优先将稳定字段设为固定值并逐项缩小问题范围。不要仅凭 `yapi_save_api` 成功断言 Mock 可用。
- `code`、`success` 等值要符合调用方真实的成功判定；先查当前请求层规则，不能假设所有项目使用相同成功码。
- 只有用户要求验证 Mock 或联调时才做对应验证。写入回读、Mock 可运行、前端浏览器验证、真实后端联调分别报告，不互相替代。若必须检查 YApi 页面或浏览器表现，遵循全局规则仅使用 Codex `@Chrome`，不使用终端或 curl 访问网页。
- **web-base PIM** 如果接口走 Vite Mock 代理，改 path 后还要检查对应代理规则；更具体的代理匹配应排在通用前缀之前，避免请求落入错误目标。先读当前项目配置，不把 `/dev` 前缀或某条代理规则推广为通用要求。
