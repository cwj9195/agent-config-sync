# ZenTao MCP 禅道操作

## 1. 目标与核心原则

以 `zentao-11-3` MCP 为唯一入口，完成项目、执行、需求、任务、Bug、测试单和测试用例的读取、编写、状态变更与结果核验。禁止调用 `zentao-aipper`。

默认账号：`caiwenjia`（蔡文嘉）。

禁止在 Skill、脚本、日志或回复中保存密码、Token、Cookie、会话密钥或完整认证请求头。

### 核心不变量

1. **读取事实优先**：实体状态、项目、执行、版本、负责人等必须以实时读取结果为准，不根据历史记录或 ID 猜测。
2. **写操作必须确认**：创建、更新、完成、解决 Bug、批量更新、提交测试结果等写操作，在真正写入前必须向用户展示最终字段并取得明确确认。
3. **写入只提交一次**：返回异常、超时或写后解析错误时，先回读当前状态，禁止盲目重复提交。
4. **写后必须回读**：不能仅依据 HTTP 200、MCP “成功”文本或 POST 返回判断成功。
5. **不伪造能力或结果**：接口不可用、数据无法验证、参数缺失时明确报告，不猜测、不虚构。
6. **局部结果不得冒充全局结果**：白名单、异常接口或未覆盖范围存在时，必须明确结果边界。

## 3. 写操作事务协议

所有写操作默认遵循：

```text
READ → VALIDATE → PREPARE → CONFIRM → WRITE_ONCE → READ_BACK
```

### READ

先读取目标实体或来源实体，确认：

* 目标 ID；
* 项目、执行及关联关系；
* 当前状态；
* 负责人；
* 与本操作相关的版本、工时、优先级、严重程度等实时字段。

### VALIDATE

只使用用户明确提供或实时读取到的数据。

缺少必要字段时不得猜测，例如：

* 项目 / 执行；
* 类型 / 优先级；
* 工时 / 截止日期；
* Bug 解决原因 / 解决版本；
* 测试用例版本 / 实际结果。

### PREPARE + CONFIRM

向用户展示最终待写入摘要。

对于批量操作，至少展示：

* 实体 ID 清单；
* 修改字段；
* 影响范围。

未获得明确确认前不得写入。

### WRITE_ONCE

确认后只提交一次。

若调用出现超时、连接中断、写后解析错误或结果不明确：

1. 不立即重试；
2. 先执行 `READ_BACK`；
3. 只有确认目标状态未发生变化且错误原因明确后，才判断是否允许再次提交。

### READ_BACK

写入后重新读取目标实体，以实际回读结果作为成功依据。

不得只依据：

* HTTP 200；
* MCP “成功”字符串；
* POST 返回体；
* 本地预期状态。

删除、批量关闭、批量解决或其他明显不可逆操作，必须另行确认明确目标范围和结果。

* 白名单没有结果时，只能表述为“白名单范围内未找到”。

### 4.2 查询流程

“上周”默认按自然周：上周一至上周日。

任务日期优先使用 `finishedDate`；没有完成日期时才使用 `openedDate`，并标注日期来源。

执行步骤：

1. 调用初始化工具确认连接状态。
2. 对白名单项目调用 `mcp_zentao-mcp_zentao_list_executions`，实时确认执行 ID。
3. 不根据项目 ID 猜执行 ID；历史执行 ID 只作为校验参考。
4. 对每个执行调用 `mcp_zentao-mcp_zentao_list_tasks`：

   * `scope=execution`
   * `scopeId=<实时执行ID>`
   * `limit=100`
   * 按任务 ID 倒序
5. **多个执行必须串行查询，不要并行。**
6. 若 `raw.total` 大于当前页数量，继续分页，并校验 `raw.page`。

### 4.3 结果有效性检查

每个任务响应至少校验：

* `task.execution == requestedExecution`
* `task.project == requestedProject`
* `openedBy.account` / `finishedBy.account` / `assignedTo.account` 数据结构有效
* 日期位于目标范围
* 默认状态为 `done` 或 `closed`，除非用户要求未完成任务

命中以下任一情况，该执行标记为**接口异常**，不得解释为“没有任务”：

* 返回已知陈旧任务 `115799` 或 `115787`
* 非目标请求却返回执行 `6872`
* 返回项目与请求项目不一致
* 请求第 2 页却返回第 1 页固定旧数据
* `assignedTo=caiwenjia` 返回空，但原始数据明显存在 `openedBy` 或 `finishedBy=caiwenjia`

### 4.4 个人任务过滤

默认认为属于当前用户的任务：

```text
openedBy.account == caiwenjia
OR
finishedBy.account == caiwenjia
```

若用户要求严格复现 ZenTao 页面 `myinvolved`：

* MCP 当前没有可靠的全局 `myinvolved` 语义时，优先按 `openedBy`、`finishedBy` 和动作记录核验；
* 不得把执行内全部任务当作当前用户任务；
* 接口过滤为空不能直接解释为用户没有任务；
* 无法核验的执行单独列出，不计入最终统计。

### 4.5 输出边界

个人任务汇总至少包含：

* 日期范围；
* 项目集 ID / 项目集名称；
* 项目 ID / 项目名称；
* 必要时显示执行 ID / 执行名称；
* 任务 ID、任务名称、状态、完成日期、消耗工时；
* 按项目汇总任务数和工时；
* 接口异常、未覆盖范围及被排除的非本人任务。

不得把白名单结果称为“全部禅道项目的全局结果”。

## 5. 任务操作

### 创建任务

当用户要求“帮我写一个禅道任务”：

1. 确认需求 ID、Bug ID，或用户明确提供的项目与执行。
2. 读取来源详情，提取标题、业务目标、验收条件、模块和已有约束。
3. 形成任务草案：

   * 名称
   * 类型
   * 优先级
   * 执行
   * 负责人
   * 预计工时
   * 截止日期
   * 描述
   * 验收标准
4. 来源为需求或 Bug 时，优先使用 `createTaskFromStory` / `createTaskFromBug`。
5. 按“写操作事务协议”确认、写入、回读。

任务描述建议区分：

* 目标
* 实现范围
* 非目标
* 验收标准
* 风险和依赖

不得把用户未提供的接口、字段、枚举、工时或日期写成事实。

### 更新 / 完成任务

* 更新任务：只修改用户明确要求的字段，不覆盖未提及字段。
* 完成任务：先核对当前状态、剩余工时、实际消耗和完成说明。
* 批量更新：确认 ID 清单和变更字段；写入后按工具能力逐条或抽样回读核验。

## 6. Bug 操作

### 6.1 Bug 核心门禁

**ZenTao `active` 只表示禅道状态，不等于问题当前仍可复现。**

只有满足以下之一，才允许进入 `resolution=fixed` 的解决流程：

#### A. 本次实际修复

```text
成功复现
→ 确认根因
→ 完成本次代码/配置修复
→ 回归验证通过
```

#### B. 已由既有改动修复

必须同时具备：

* 可追溯的既有改动事实；
* 准确解决版本；
* 回归验证证据；
* 向用户展示证据；
* 用户明确确认解决。

以下情况必须停止解决流程：

* 未复现；
* 当前无法验证；
* 当前行为符合预期，但找不到可追溯修复事实；
* 只有 ZenTao `active` 状态或历史描述；
* 用户只说“已经好了”，但无法确认实际修复和解决版本。

此时：

* 不为关闭 Bug 而制造无效代码改动；
* 不增加临时绕过；
* 不虚构根因；
* 不调用 `resolveBug`；
* 报告实际核验事实和缺口。

### 6.2 Bug 解决流程

1. 调用 `getBugDetail`，确认：

   * Bug ID
   * 项目 / 执行
   * 标题
   * 状态
   * 严重程度 / 优先级
   * 复现步骤
   * 关联需求 / 任务
   * 当前负责人
2. 按复现步骤使用已授权环境、本地代码或可重复自动化验证当前问题。
3. 满足“Bug 核心门禁”后，确认真实根因、实际修复方案和解决版本。
4. 准备：

   * `resolution=fixed`
   * `resolvedBuild=<真实解决版本>`
   * `comment=<固定三行格式>`
5. 展示最终字段并获得用户确认。
6. 只调用一次 `resolveBug`。
7. 回读并至少核验：

   * `status=resolved`
   * `resolution=fixed`
   * `resolvedBuild`
   * `resolvedBy`
   * `resolvedDate`
   * 最新解决动作
   * 完整备注

### 6.3 解决版本

必须填写真实解决版本。

用户未明确指定解决版本时，默认按“主干”处理；用户明确提供其他真实版本时，优先使用用户指定版本。若实时读取结果显示当前版本与主干不一致，必须以实时结果为准并说明，不得猜测。

界面显示“主干”时，接口值使用：

```text
trunk
```

不得把界面显示文本和接口键混用。

### 6.4 Bug 解决备注格式

`resolution.comment` 必须严格使用：

```text
产生原因：<可验证的技术或业务根因>
解决方案：<本次实际执行的修复方案>
改进措施：-
```

要求：

* 根因不能只重复现象；
* 解决方案必须对应实际改动；
* 无改进措施时固定填写 `-`；
* 三行之间不插空行；
* 不使用 Markdown 标题；
* 标签与内容必须同一行。

### 6.5 MCP 写后解析错误

若 `resolveBug` 返回类似：

```text
Cannot read properties of undefined (reading 'id')
```

不得立即重试。

先回读：

* 若状态已经 `resolved`：以回读为准，判定写入已完成；
* 若仍为 `active`：检查接口字段校验，尤其是 `resolvedBuild` 等必填字段，再决定后续处理。

### 6.5.1 zentao-11-3 会话失效读取处理

若 `getBugDetail` 读取失败并出现：

```text
Cannot read properties of undefined (reading 'id')
```

或返回结构无法解析：

1. 不得将其解释为 Bug 不存在、无权限或当前没有数据。
2. 先确认本次只是读取失败；不得调用 `resolveBug`、`activateBug` 或其他写操作。
3. `initZentao` 只能用于检查配置，不能视为刷新已经存在的 `zentao-11-3` 实例或 Session。
4. 优先重启或重新加载当前 `zentao-11-3` MCP 进程，然后只重新调用一次 `getBugDetail`。
5. 重启后读取成功，使用新结果继续执行 `READ → VALIDATE`；仍然失败时，明确报告“`zentao-11-3` 会话或解析异常”，不得切换到其他 MCP，也不得写回。
6. 只有获得完整 Bug 详情、当前状态、项目或执行信息及复现依据后，才能进入 Bug 核心门禁和写操作确认。

当前宿主未提供 MCP 重启入口时，必须明确请求用户重启或重新加载 MCP；不得通过猜测、旧会话结果或未经 Skill 授权的原始接口绕过读取门禁。

### 6.6 Legacy Bug 降级

只有同时满足以下条件才允许使用 `/bug-resolve-<bugId>.json`：

* MCP 已确认无法完成写入；
* 用户已经确认最终解决字段；
* 当前会话存在已认证 Legacy 客户端；
* Bug 当前仍为 `active`；
* 已满足“Bug 核心门禁”。

只允许发送一次写入。

随后必须读取：

```text
/bug-view-<bugId>.json
```

并按回读结果核验。

回复中必须明确标注：

```text
Legacy 接口降级写回
```

不得描述为“MCP 源码已经修复”。

## 6.7 Bug 关联代码提交

用户明确要求提交暂存或关联 Bug 时，按以下流程执行：

```text
READ_STAGED → VALIDATE_SCOPE → PREPARE+CONFIRM → COMMIT_ONCE → READ_BACK
```

* `READ_STAGED`：读取仓库边界、`git status --short`、`git diff --cached --stat`、暂存差异和未暂存差异。
* `VALIDATE_SCOPE`：只允许提交本会话实际修改的代码块；混合文件使用交互式补丁或独立暂存索引选择性提交，逐块核对暂存差异，无法确认归属时排除或请求确认。禁止默认把其他会话已有的暂存内容移出再移回，禁止 `git add -A`、`git commit -a`；`apps/pim` 使用 `git -C apps/pim ...`，根仓库其他改动和子模块指针不自动纳入。
* 若发现其他会话已有暂存内容：优先保留原暂存区不变，使用临时 `GIT_INDEX_FILE` 构造只包含本会话改动的提交；若无法可靠隔离，停止提交并说明原因。普通 `git commit` 会提交全部暂存内容，`git commit -- <path>` 也可能提交该文件中其他已暂存代码块。
* `PREPARE+CONFIRM`：展示仓库、暂存文件与统计、排除项、Bug 号和提交信息。Bug 修复提交信息必须符合：

```text
fix(<scope>): #<bug号> <说明>
```

`<scope>` 使用实际模块或范围，`<bug号>` 必须来自用户或实时核验；禁止不带 scope 的 `fix: ...`、猜测 Bug 号或保留占位符。例如：

```text
fix(pim): #18007 修复申请单暂存逻辑
```

* `COMMIT_ONCE`：确认后只执行一次针对暂存区的 `git commit`；失败或结果不明确时先回读，禁止盲目重试。
* `READ_BACK`：回读提交 ID、信息、文件、`git status --short`、暂存区是否为空，并确认未暂存差异仍按预期保留。

若提交发生在 Git 子模块中，必须分别报告子模块提交 ID；根仓库子模块指针是否提交，除非用户明确要求，否则不自动处理。

Bug 状态写回与代码提交是两个独立写操作：即使其中一个成功，另一个结果不明确也必须单独回读，不得把 Git 提交结果当作 ZenTao 写回证据，反之亦然。

## 7. 测试单与测试用例

### 7.1 基本规则

1. 先读取测试单和关联用例，确认 `caseId` 确实属于目标测试单。
2. 创建用例时只使用真实存在的：

   * 前置条件
   * 步骤
   * 预期结果
   * 优先级
   * 模块
3. MCP `runTestCase` 支持：

   * `pass`
   * `fail`
   * `blocked`
   * `skipped`
4. “开始测试”不等于提交 `pass`；没有实际结果时不得擅自写入。
5. 写入测试结果后必须回读测试单结果，确认用例、结果和执行人。

### 7.2 REST v1 降级契约

当 `runTestCase` 出现以下情况，可考虑 REST v1：

* `real` 字段校验失败；
* 结构化 `steps` 被错误序列化成字符串；
* MCP 返回成功但回读不到结果。

接口：

```text
POST /api.php/v1/testcases/:caseId?runID=<testTaskId>&version=<caseVersion>
```

请求体必须为 JSON：

```json
{
  "steps": [
    {
      "result": "pass",
      "real": "实际结果"
    }
  ]
}
```

专属约束：

* `caseId` = 测试用例 ID；
* `runID` = 测试单 ID；
* `version` 必须从用例详情实时读取，禁止固定为 `1`；
* `steps` 必须保持原用例步骤顺序；
* 每一步必须提供 `result` 和 `real`；
* REST 支持 `pass` / `fail` / `blocked` / `n/a`；
* MCP 的 `skipped` 调 REST 时转换为 `n/a`；
* 必须发送 JSON，禁止把数组通过 `application/x-www-form-urlencoded` 拼成字符串。

### 7.3 REST 降级前置条件

降级前必须确认：

* `caseId` 属于目标 `runID`；
* `version` 准确；
* 用户已经确认最终结果；
* 每一步实际结果明确；
* 当前存在可用且已认证的 REST 会话。

如果不存在认证 REST 能力、准确地址或必要字段，报告能力缺口，不伪造回写。

按照“写操作事务协议”：

```text
CONFIRM → WRITE_ONCE → READ_BACK
```

写入后使用 `getTestTaskResults` 核验：

* 测试单；
* 用例 ID；
* 最新结果；
* 执行人；
* 最新执行时间。

回读不到目标结果时标记为：

```text
写入未核验
```

不得宣称成功。

回复中注明：

```text
REST v1 降级回写
```

不得描述为“MCP 源码已经修复”。

## 9. 无浏览器原则

默认只使用 ZenTao MCP 和本地只读处理。

仅在以下情况考虑浏览器作为人工核验手段：

* MCP 无法取得某项目必要数据；
* 必须严格复现 ZenTao 页面 `myinvolved` 语义；
* 必须确认分页、执行或项目错配；
* 按 Bug 复现步骤验证问题，但 MCP、本地代码和自动化验证不足以判断。

如果用户明确要求“不使用浏览器”，必须保留接口异常与未覆盖范围，不得用猜测补全。
